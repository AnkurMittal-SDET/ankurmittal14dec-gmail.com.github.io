How I Work

02 / principles
01

A passed test that hides the real issue is worse than a failed one

A green tick on the surface doesn't mean the backend agrees. I've caught critical defects — like pricing and shipping calculations that looked correct in the UI but didn't match the underlying data — by cross-checking application logs, API payloads, and databases directly rather than trusting the front end alone.

02

Traceability is what makes a release defensible

I build requirement-traceability pipelines as a matter of course, not an afterthought — so that when a stakeholder asks "was this actually tested," the answer is in the tooling, not in someone's memory.

03

Risk should decide where testing effort goes

Not everything deserves equal coverage. I use risk-based testing to focus effort on what would actually hurt the business if it broke, rather than testing everything to the same depth by default.

04

Feedback to developers should be evidence, not opinion

When a build doesn't match spec, I bring the exact values — spacing, data, calculations — side by side with the design or requirement, and raise it as a collaborative fix rather than a blame exercise.
